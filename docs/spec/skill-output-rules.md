# skill-output-rules (스킬 출력 자기 검사 규칙)

- 상태: 추천안 채택(ADR 0016, juhan 확인 2026-11-09). R14~R21은 ADR 0018(juhan 확인 2026-11-10 07:41). 작업 카드 `docs/tasks/T-022-first-use-skill-depth.md`, `docs/tasks/T-024-role-allocation-criteria.md`.
- 근거: 지시문 0016(첫 실사용 supplier-carbon-survey 결과와 독립 검토), juhan 지시 2026-11-10(인간·AI·소프트웨어 역할 배분 기준, R14~R21).
- 채점 표는 `docs/spec/data/skill-output-rules.md`(절 번호가 같다). 테스트가 규칙 번호를 읽는다.
- 스킬 `/scorecard`(`.claude/skills/scorecard/SKILL.md`)는 결과를 내기 전에 이 규칙을 모두 본다. 엔진(분류 트리·대조·판정)은 이 규칙을 모른다.

## 1. 범위

- 스킬이 쓰는 글: 단계 `ai`(`reason`, `actions`, `now`, `change`, `check`, `gate_note`, `roles`, `judgment`, `execution`, `accountability`, `basis`, `varies`), 케이스 메모(`scenario`, `summary`, `stated_numbers`, `self_check`, `open_questions`, `end_state`, `purpose`, `done_when`, `facts`, `assumptions`, `tools`, `transitions`), 확인 파일(`confirmed_in`), 대화에서 하는 말.
- 범위 밖: 숫자·판정(엔진 JSON 값만 옮긴다, CLAUDE.md 절대 원칙 4), HTML 배치(report.md 12절).
- 스킬 출력은 AI라 골든 테스트가 안 된다. 대신 사람이 아닌 새 reviewer가 이 규칙으로 채점한다(6절).

## 2. 판단 기준 한 줄

- "이 단계에서 무엇을 판단하고, 무엇을 실행하고, 누가 책임을 인수하는가. 그중 규칙으로 할 수 있는 것은 무엇인가."
- 분류 코드를 고르는 일이 아니라 이 질문에 답하는 일이다. 업무 이름만 보고 역할을 정하지 않는다.
- 세 역할: 소프트웨어(입력·규칙·결과를 명시해 반복 실행: ②, 고정 모델 ②M, 이미 손 없이 돌면 ①), AI(맥락·의도·예외 해석: ③), 인간(책임 인수, 의사·가치·관계·신뢰: ④).

## 3. 규칙

### R1 출처 없는 단정 0건

- 판단 문장마다 출처가 셋 중 하나다: `stated`(사용자가 말함), `inferred`(AI 추정), `default`(기본값).
- `inferred`·`default`인 내용은 문장 자체를 추정형으로 쓴다. "지금은 AI가 한다" → "현재 방식은 확인되지 않았다. AI가 하고 있다면 규칙으로 바꿀 후보다."
- 자기 검사: 문장마다 "근거가 intake.md(또는 대화에서 사용자가 한 말)에 있는가"를 본다. 없으면 출처를 `inferred`로 바꾸고 문장을 추정형으로 고친다. 답 키면 `inferred` 목록에 적는다.
- 동작 `source: stated`는 사용자가 준 말 그대로일 때만이다. 방법·조건("규정에 맞춰", "상황에 맞춰")을 붙이면 말한 동작(`stated`)과 붙인 방법(`inferred`)으로 나눈다. 내용을 질문·`open_questions`로 묻는 동작은 `stated`가 아니다.

### R2 집계는 stated만

- 스킬은 셈하지 않는다. 셈은 스코어카드(`summary.stated`, `summary.tentative`)가 한다(report.md 12.3).
- 스킬은 셈이 갈리도록 출처를 바르게 적는다: 동작마다 `source`, 짐작한 답은 `inferred`.
- 대화에서 셈을 말할 때는 `summary.stated`의 값을 말하고, `summary.tentative`는 "확인하면 바뀔 수 있음"으로 따로 말한다.

### R3 ①은 손이 안 가는 경우만

- ①은 "지금 이미 사람 손 없이 돌아간다"일 때만이다.
- 사람이 도구를 손으로 조작하면(클릭·복사·첨부·폴더 이동) ①이 아니라 ② 후보다.
- "기존 도구에 이 기능이 있을 수 있다"는 ①이 아니라 `check`(확인할 것)에 적는다.

### R4 추천 문장에 이유

- 단계 `reason`은 결론과 이유를 같이 쓴다. 결론만 쓰지 않는다.
- AI 판단과 규칙 의견이 다르면 추천 결론과 이유를 먼저 쓴다. "다릅니다"로 끝내지 않는다. 예: "담당자 확인 유지 권장. 숫자 대조는 자동화할 수 있지만 사업장 범위 판단이 들어 있다."
- 먼저 확인할 것(제안)은 효과를 말한다. 효과를 계산할 수 없으면 왜 이것을 먼저 보라는지 말한다.

### R5 종료점 문장

- `check`를 돌리지 않고 스코어카드를 내면 늘 `end_state`를 "업무 구조 검토 완료. 지금 제출할 것 없음."으로 적는다. 구조만 보자고 했을 때, 자료를 주지 않았을 때, 답을 기다리는 질문이 남았을 때 모두다(데이터 채점 표: 자료 없이 끝냈는데 없거나 다른 문장이면 실패).
- 자료를 넣고 `check`를 돌렸으면 판정 문장(judgment.json)이 종료점이다. `end_state`를 적지 않는다.
- 대화의 마지막 줄은 `end_state` 문장이다. 다시 묻는 질문은 그 앞에 둔다.

### R6 동작 단위로 나눈다

- 단계마다 사람이 실제로 하는 동작을 먼저 적는다(`actions`). 받기·열기·찾기·읽기·옮겨 적기·비교하기·판단하기·쓰기·붙이기·보내기·기록하기 수준이다.
- 설명에 없는 동작은 "이 단계에서 보통 사람이 하는 동작"을 추정하고 `source: inferred`로 적는다.
- 동작마다 `proposed`를 정한다. 단계 담당은 동작 분류의 합으로 정하고, 섞이면 `reason`에 나눈 내용을 쓴다.

### R7 ②는 규칙으로 검사할 수 있다까지

- 시험 전이다. "같은 결과를 낸다"고 단정하지 않는다.
- 규칙으로 되는 부분과 안 되는 부분을 같이 쓴다. 예: "빈칸·숫자 형식·허용 단위는 규칙으로 검사할 수 있다. 보고 기간·범위가 원본 뜻과 맞는지는 규칙으로 안 된다."

### R8 ③도 동작 단위로

- "사유가 건마다 다르다"로 단계 전체를 ③으로 보내지 않는다.
- 사유가 몇 가지로 묶이면 양식(②)이고, 묶이지 않는 건만 ③이다.
- 묶이는지 모르면 "묶이지 않아"로 쓰지 않는다. "묶이는지 확인되지 않았다. 묶이면 양식(②), 안 묶이는 건만 ③"으로 쓴다. `reason`에는 코드 대신 업무 말("양식(규칙)", "AI 초안 + 담당자 확인")로 쓴다.

### R9 담당자 확인은 흐름에 붙인다

- "사람 게이트"라고 쓰지 않는다. "담당자 확인"으로 쓰고 누가·언제·무엇을 확인하는지 쓴다(`gate_note`).
- 이미 사람이 확인하는 단계(원본 대조, 최종 승인)가 있으면 그 단계에 합친다. 예: "4단계 원본 대조 때 함께 본다."
- 보내기·전달 단계의 확인은 보내기 전에 둔다.
- 엔진의 부가 행은 지우지 않는다. 화면 문장만 `gate_note`로 바꾼다.
- `gate_note`는 엔진이 `human_gate` 행을 붙일 때만(틀렸을 때 영향이 외부·안전·법적) 화면에 나온다. 영향을 모르는데 보내기 전 확인을 권하면 `reason`에 그 말을 쓰고 "결과가 외부로 나가나"를 질문·`open_questions`로 남긴다.
- 보내기 전 확인을 둘 때는 보내기 동작이 확인할 것을 만드는 동작보다 뒤인지 본다.

### R10 사용자 숫자는 준 모양대로

- 사용자가 준 숫자는 `stated_numbers`에 그대로 적는다. "연 1회, 집중 기간 10주, 주 10건"을 weekly·rare 중 하나로 바꾸지 않는다.
- 숫자가 무엇의 시간인지 바꾸지 않는다. "예외 1건 처리에 15분"은 예외 1건 전체이지 한 단계의 시간이 아니다.
- 질문 답(`frequency` 등)은 엔진용으로 따로 채우고, 짐작했으면 `inferred`에 적는다.
- 업무 요약 네 줄(`summary`: 규모, 현재 처리, 예외율, 결과 전달)도 사용자 말로 쓴다.

### R11 질문은 추천이 바뀌는 것만 3개까지

- 한 번에 묻는 질문은 답에 따라 추천이 바뀌는 것만, 많아야 3개다.
- 코드로 고르게 하지 않는다. "safety_legal인가요?" → "이 자료는 내부 분석에만 쓰나요, 외부 공시나 공식 제출에도 쓰나요?"
- 한 단계에 두 일이 섞이면 나누어 묻거나 "두 활동이 있다"고 쓴다. 건수도 따로 센다(2건/10건).
- 묻지 않은 모름 항목은 `open_questions` 또는 `inferred`로 남긴다. "확인하면 바뀔 수 있음"으로 보인다.

### R12 확인 기록은 실제로 확인한 것만

- 사용자가 대화에서 맞음/바꾸기를 고른 단계만 확인 파일에 적는다. 최상위에 `confirmed_in: conversation`을 둔다(report.md 12.5).
- "검증 자료 없이"를 "모두 맞음"으로 해석하지 않는다. 고르지 않은 단계는 적지 않는다(확인 전).
- 바꾸기는 사유 한 줄을 받는다(report.md 5절).
- 고른 단계가 없으면 확인 파일을 쓰지 않고 `--review` 없이 `open`을 부른다. 빈 `steps`와 `confirmed_in: conversation`은 확인한 것처럼 보인다.

### R13 자료 성격을 적는다

- 가상 시나리오나 연습 입력이면 `scenario: virtual`을 적는다. 스코어카드 맨 위에 "가상 시나리오 기반. 실제 운영 수치·검증 결과 아님"이 붙는다.
- 사용자가 자기 업무라고 하면 `real`, 모르면 적지 않는다.

### R14 판단·실행·책임을 나눈다

- AI 판단 단계마다 `judgment`(판단), `execution`(실행과 누가), `accountability`(책임 인수 지점)를 따로 쓴다. 책임 지점이 없으면 없다고 쓰고 잘못되면 어디서 드러나는지 쓴다.
- 한 단계에 AI가 판단하고 소프트웨어가 실행하고 인간이 승인하는 구성을 `roles`로 나눈다. 단계 담당은 중심 역할 하나다.

### R15 책임만으로 사람에게 준비·실행을 주지 않는다

- 책임이 사람에게 있다는 이유로 자료 모으기·요약·목록·기록까지 `human`에 두지 않는다.
- `human`에는 사람이 직접 결정하는 지점(승인, 약속, 이해관계 조정)만 쓴다. 준비는 `ai`·`software`에 지원 범위로 쓴다.

### R16 배분 근거는 다섯 질문으로

- `basis`는 다섯 질문에 답한다: 무엇이 달라지나, 입력값인가 맥락 해석인가(`varies`), 무엇을 규칙으로 쓸 수 있나, 어디에 사람의 의사·책임이 필요한가, 결과를 누가 어떻게 확인하나.
- 입력값만 달라지고 처리 규칙이 같으면 소프트웨어다. 반복돼도 매번 맥락 해석이 필요하면 AI 역할이 남는다.

### R17 도구 제안은 열한 칸을 채운다

- `tools`마다 `name`, `steps`, `function`, `input`, `process`, `output`, `reduces`, `exceptions`, `existing`, `new`, `burden`을 쓴다(파서가 빈 칸을 막는다).
- `exceptions`는 AI·사람에게 다시 넘길 조건이다. `existing`은 기존 기능으로 해결할 범위, `new`는 새로 개발할 범위다.
- `burden`은 개발·유지보수 비용과 호출·결과 확인 부담을 보고 실제로 일이 줄어드는지 쓴다. 재지 않았으면 재지 않았다고 쓴다.

### R18 역할 전환은 근거를 적는다

- `transitions`마다 바꾸는 조건(`condition`)과 필요한 사례·검증 결과·운영 데이터(`evidence`)를 쓴다.
- AI의 자신감만으로 맡기는 범위를 넓히지 않는다. "AI가 잘할 것이다"는 근거가 아니다.

### R19 측정 없는 점수·절감률 0건

- 점수, 절감률, 퍼센트, 시간 절약은 엔진 JSON이나 `stated_numbers`에 있을 때만 쓴다.
- `tools`·`transitions`·`basis`·대화에 만든 숫자를 쓰지 않는다. 효과는 "재지 않았다"와 검증 방법으로 쓴다.

### R20 세 역할을 억지로 채우지 않는다

- 근거가 있는 역할만 `roles`에 적는다. 없는 역할은 비운다. 화면에 "역할 없음"으로 보인다.
- 모든 단계에 인간·AI·소프트웨어를 하나씩 넣지 않는다.

### R21 업무 이해는 사실과 가정을 나눈다

- `purpose`(목적)와 `done_when`(완료 조건)을 쓴다.
- `facts`에는 사용자가 말한 것만, `assumptions`에는 AI가 짐작한 것을 "확인되지 않았다"로 쓴다. 결론을 바꿀 가정은 질문(R11)으로 묻는다.

## 4. 자기 검사 기록 (`self_check`)

- 스킬은 `answers.yaml`을 쓰기 직전에 R1~R21을 본다. 실패가 있으면 고친 뒤 다시 본다.
- 맞대어 본다: 물은 질문과 `open_questions`의 내용이 `reason`·`actions`·`now`에 단정형이나 `source: stated`로 적혀 있으면 R1 실패다. 추정형과 `inferred`로 고친다.
- 결과를 `self_check`에 규칙마다 한 줄 적는다: `{rule: R1 출처 없는 단정 0건, result: pass}`. 수용 규칙 R1~R5는 늘 적고, R6~R21은 실패했거나 `note`가 있을 때만 적어도 된다. 고칠 수 없는 실패는 `result: fail`과 `note`(무엇이 남았나)로 남긴다.
- 규칙 이름은 데이터 3절 채점 표의 "규칙" 칸 그대로다. 스코어카드 7구역 펼쳐 보기에 보인다.

## 5. 엔진과의 경계

- 스킬이 쓴 글은 Core가 바꾸지 않고 옮긴다(case-schema.md 4.15). 분류·대조·판정은 바뀌지 않는다.
- 셈("말한 것만"과 "확인하면 바뀔 수 있음"), 제안 순서, 담당자 확인 문장 고르기는 Core `ScorecardBuilder`가 한다(report.md 12.3·12.4).

## 6. 채점 (지시문 8.2)

- `docs/cases-public/answers/`의 사례 5건(case-01, case-20, case-22, case-31, case-48)을 스킬에 넣는다.
- 카드를 본 적 없는 새 reviewer가 데이터 채점 표로 사례마다 R1~R5 통과/실패를 매긴다. R6~R21은 지적만 적는다.
- R14~R21은 수용 기준이 아니다(T-024). 다음 채점에서 지적으로 모은다. 한 번 채점해 실패 기준이 흔들리지 않으면 R14·R19부터 수용으로 올린다(ADR 0018 결정 5).
- 실패가 하나라도 있으면 스킬 본문을 고치고 그 사례를 다시 넣는다. 다섯 사례 모두 R1~R5 통과가 M2-2 수용 기준이다.
- 채점 결과는 카드 T-022에 적는다. 첫 실사용 입력과 독립 검토 지적은 `docs/cases-public/review-01.md`(가상 시나리오 표시)로 남긴다.
