먼저 확인할 것

1단계 회신 받아 모으기

  1. 기존 기능으로 되는지 확인
  2. 안 되면 새로 만들지 판단
  3. 만들기로 하면 의뢰서

절감 효과가 가장 크다고 확인된 건 아니다. 기존 설정으로 해결될 가능성이 있어 비용을 들이기 전에 먼저 확인할 항목으로 골랐다. 이 단계의 판단은 추정·기본값에 기대고 있어 확인하면 바뀔 수 있다.

고른 규칙과 만들기로 정한 뒤(구현 담당자 안내)

② 단계 가운데 아직 사람이 하는 첫 단계다.

scorecard build ai-actions --step 1

담당자 확인
  • 2단계 예외 건 담당자 검토: 규칙으로 판단이 안 되는 예외 건은 담당자가 검토한다.
    엔진 문장판단 기준을 일부만 글로 쓸 수 있으므로(partial) 예외 건은 사람이 검토한다.
  • 3단계 담당자 확인: 보내기 전에 담당자가 초안을 읽고 고친다. 4단계 원본 대조 때 함께 본다.
    엔진 문장틀리면 외부에 영향이 있으므로(external) 이 단계 뒤에 사람 게이트를 둔다.
  • 4단계 담당자 서명: 담당자가 최종 확인·서명한다.
    엔진 문장수정 자료 재검토와 전체 최종 승인 두 활동이 있다. 둘 다 담당자가 판단한다.
남는 위험
  • 3단계 확인 요청 쓰기: AI 초안이 틀릴 수 있다. 자동 승인하지 않고 담당자가 확인해 잡는다.

이번 실행에는 비교 자료를 넣지 않았다. 실제 검증 때 무엇을 오류로 셀지 먼저 정한다.

  1. 단계마다 맞는지 확인한다(맞음/바꾸기): 4단계.
개선을 진행하려면
  1. 먼저 확인할 것부터 본다. 기존 기능으로 되면 끝, 안 되면 새로 만들지 판단하고, 만들기로 하면 의뢰서를 낸다.
  2. AI가 가정한 답을 확인한다: 1단계 처리 주기.
실제 효과까지 검증하려면(선택)
  1. 실제 효과까지 보려면 사람이 만든 결과와 AI 적용 결과를 한 벌씩 준비해 비교한다.
  2. 실제 검증 때 무엇을 오류로 셀지 먼저 정한다.
  3. 개선 전후를 비교하려면 단계별 건당 시간을 잰다: 2, 4단계.
구현·검증 담당자 안내
  1. 기준 자료(사람이 만든 결과)는 reference/, 결과 자료(AI 적용 후)는 candidate/에 넣고 case.yaml에 inputs·compare·thresholds를 적은 뒤 scorecard check를 돌린다.
  2. 단계 확인 결과는 확인 파일(--review)로 open에 넣는다.
  3. 만들기로 정하면 scorecard build ai-actions --step 1 명령으로 의뢰서 번들을 쓴다. 내보내기 전에 export-check.md에 사람이 확인을 적는다.

업무 요약과 입력 기록

  • 규모연 1회, 집중 기간 10주, 주 10건 안팎
  • 현재 처리담당자 한 명이 메일로 받아 손으로 정리한다
  • 예외율열 건 가운데 두세 건은 다시 묻는다
  • 결과 전달승인한 자료를 분석 담당에게 넘긴다
사용자가 준 숫자(그대로)
  • 연 1회, 집중 기간 10주
  • 주 10건
  • 예외 1건 처리에 15분(예외 1건 전체 기준, 한 단계의 시간이 아님)
입력 원문 보기
# 합성 예시. 실제 업무·값 없음. 가상 시나리오. 해마다 한 번, 집중 기간 10주 동안 협력 업체 설문 회신을 받는다. 주 10건쯤 온다. 담당자가 메일을 열어 첨부를 내려받고, 빈칸과 단위를 본다. 틀린 곳이 있으면 업체에 다시 물어본다. 예외 한 건을 처리하는 데 15분쯤 걸린다. 고친 자료를 원본과 대조해 승인하고 분석 담당에게 넘긴다. 검증 자료 없이 구조만 봐 달라.
단계 흐름
  1. 회신 받아 모으기 규칙 자동화 검토
  2. 빈칸·단위 검사 규칙 자동화 검토
  3. 확인 요청 쓰기 AI 초안 + 담당자 확인
  4. 원본 대조·최종 승인 담당자 직접 처리
