# 0018. 역할 배분 기준: 인간·AI·소프트웨어

- 날짜: 2026-11-10
- 상태: 추천안 채택(리드, ADR 0005 결정 3). **범위는 juhan 확인(2026-11-10 07:41, 결정 카드 "스킬과 스코어카드에만 적용")**. 결정 1·2·3은 뒤집기 쉽게 두었다(대안 절).
- 관련: juhan 지시(2026-11-10 07:39, 프로젝트 채팅, "이걸 스코어카드 판단기준에 적용해"), ADR 0003, ADR 0008 결정 1, ADR 0013, ADR 0016, 카드 `docs/tasks/T-024-role-allocation-criteria.md`.
- 지시문 2절 8·10(실제 자료·회사 자료 금지)은 바꾸지 않는다. 바꾸자는 제안도 하지 않는다.

## 배경

- juhan이 분석가 지시를 주었다. 업무를 판단·실행·책임으로 나눠 인간·AI·소프트웨어의 역할을 배분하고, AI의 작업을 줄일 도구와 역할이 바뀌는 조건을 제안하라는 것이다. 출력은 네 부분(① 업무 이해, ② 단계별 역할 배분 표, ③ 개선 제안, ④ 검증 방법과 역할 전환 조건)이다. 측정 근거 없는 점수·절감률은 만들지 않는다. 세 역할을 억지로 채우지 않는다.
- 지금 스킬은 단계 담당 하나(①~④, ②M)와 동작 목록을 쓴다. 한 단계 안의 판단·실행·책임, 도구 제안, 역할 전환 조건을 적을 자리가 없다.

## 결정

1. **범위: 스킬과 스코어카드만.** 분류 트리(Q1~Q4, SIGNOFF, PARTIAL, GATE), 엔진(대조·지표·판정), `examples/**/expected/**`, `tools/oracle/`은 그대로다. juhan 확인(2026-11-10 07:41).
2. **대응.** 소프트웨어 = ②(미리 학습해 고정한 모델은 ②M), AI = ③, 인간 = ④. ①은 지금 이미 사람 손 없이 돌아갈 때만이다(ADR 0016의 좁은 ①). "기존 기능으로 해결할 범위"는 도구 제안의 `existing`과 단계 `check`에 쓴다. 단계 담당은 중심 역할 하나이고, 한 단계 안의 다른 역할은 `roles`에 적는다.
3. **답 파일 선택 키(case-schema.md 4.16).** 단계 `ai`에 `roles {human, ai, software}`, `judgment`, `execution`, `accountability`, `basis`, `varies`. 최상위에 `purpose`, `done_when`, `facts`, `assumptions`, `tools`(열한 칸 모두 필수: `name`, `steps`, `function`, `input`, `process`, `output`, `reduces`, `exceptions`, `existing`, `new`, `burden`), `transitions`(`step`, `from`, `to`, `condition`, `evidence`). 모두 선택이다. Core는 형식만 보고 옮긴다. 분류·대조·판정·셈에 쓰지 않는다. `burden`은 지시 4절 끝의 "개발·유지보수 비용과 호출·확인 부담 검토"를 담으려고 리드가 더했다.
4. **판 번호.** classification.json은 schema 2 그대로다. 역할 배분은 적은 단계에만 `gate_note` 뒤에 쓴다(ADR 0016 결정 2와 같은 방식). scorecard.json도 schema 2 그대로다. 최상위 `allocation`과 단계 `allocation`은 메모가 있을 때만 쓴다. 받던 입력에서 속성을 빼거나 뜻을 바꾸지 않아 ADR 0008 결정 1의 올림 조건이 아니다. 기존 골든 7종(scorecard.json·html)과 `examples/**/expected/**`는 바이트까지 그대로다.
5. **스킬 규칙.** `SKILL.md`를 지시대로 다시 쓴다(판단·실행·책임, 다섯 질문, 책임만으로 사람에게 준비·실행을 주지 않음, 도구 제안, 역할 전환 조건, 네 부분 출력). 자기 검사 규칙 R14~R21을 `skill-output-rules.md`에 더한다. 수용 규칙은 R1~R5 그대로다. R14~R21은 다음 채점에서 지적으로 모으고, 실패 기준이 흔들리지 않으면 R14(판단·실행·책임)와 R19(측정 없는 점수·절감률 0건)부터 수용으로 올린다. 지금 올리면 T-022 채점(R1~R5)을 다시 돌려야 하고 새 규칙의 채점 기준이 한 번도 검증되지 않았기 때문이다.
6. **HTML.** 메모가 있을 때만 업무 이해, 단계마다 세 역할(없는 역할은 "역할 없음")과 판단·실행·책임·달라지는 것·배분 근거, 개선 제안 카드, 검증 방법과 역할 전환 조건 구역과 그 CSS를 쓴다. 일곱 구역(지시문 3.5)은 그대로다. Cli는 표시만 한다. 점수·절감률이 없다.

## 대안 (juhan이 고르면 바꾼다)

- **B. 규칙 트리 질문도 바꾼다.** 질문 10개에 "판단이 맥락 해석인가", "책임 인수 지점인가" 같은 질문을 더하고 트리 잎을 역할 배분 기준에 맞춘다. 대가: classification.json schema 3, 예제 5종 `expected/` 전부 바뀜(ADR 0004 expected 변경 규칙), oracle `classify.py` 새 판, 지시문 3.2·3.3 변경. juhan이 고르지 않았다(2026-11-10 07:41).
- **C. 역할 배분을 늘 쓴다.** AI 판단 단계가 아니어도 `roles`를 빈 값으로 쓴다. 공개 예제에 빈 배열만 늘고 얻는 것이 없어 고르지 않았다(ADR 0016 대안 A와 같은 이유).
- B·C로 바꿔도 Core 모델(`StepAllocation`, `CaseAllocation`)과 스코어카드 쪽은 그대로 쓴다.

## 남은 위험

- 스킬 출력은 AI라 골든 테스트가 안 된다. 테스트는 Core가 받아 옮기는 모양과 HTML 구역만 본다. 판단 깊이는 채점으로만 본다.
- 단계 담당(`ai.assignee`)과 `roles`가 어긋나도(예: 담당 ④인데 `human` 없음) Core는 막지 않는다. 채점 R14·R15로 본다.
- 도구 제안·역할 전환은 의뢰서 번들(`build`)에 아직 들어가지 않는다(LATER).
