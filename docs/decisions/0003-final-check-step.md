# 0003. 사람이 책임지는 확인·제출 단계

- 날짜: 2026-11-07
- 상태: 결정(2026-11-07, juhan): 후보 1. 세부는 끝의 "결정". 남은 질문 5개는 juhan 답 대기.
- 작성: prototyper (결정 기록 2026-11-07)
- 관련: `docs/spec/classification.md` 6.3·승인 결정 4, 지시문 3.3·12절·12.1, ADR 0004(순서·expected 변경 규칙)

표기: `[읽음]` 커밋된 파일을 읽어 확인. `[S3]` T-004 스파이크 결과(`spikes/T-004/summary.txt`). **미확인**: 실험하지 않은 추론.

## 배경

- 지시문 12.1은 비공개 케이스 하나의 기대 분류(사람 판단)를 적는다. 7단계 "최종 확인·제출"은 ④다 [읽음].
- 같은 답의 합성 사본(`tests/Scorecard.Tests/TestData/case-schema/example-12-1/case.yaml`)을 3.3 트리로 분류했다. 7단계는 ③ `Q2` + ④ `GATE`다 [S3]. 단계 자체가 ③(실행 시 AI 보조)으로 나온다.
- 7단계 답은 `rule_expressible: no`, `failure_impact: external`, `existing_feature: no`다 [읽음]. Q1에 안 걸리고 Q2에 걸린다. `external`이라 게이트 행이 붙는다.
- 사용자 단계가 ④가 되는 잎은 Q4(`rare`이고 5건 미만)뿐이다(classification.md 4.3) [읽음]. 9개 질문에 "사람이 책임지고 확인·제출하는 단계"를 가르는 질문이 없다.
- 6단계 "결과 해석 문장 작성"과 7단계는 Q2가 읽는 답(`rule_expressible`, `failure_impact`, `existing_feature`)이 같다 [읽음 classification.md 4.6, 12.1]. 답 9개 전체로도 다른 것은 `input_kind`(`free_doc` / `fixed_form`)와 `exception_rate`(50 / 0)뿐이다. 지금 답만으로는 6단계와 7단계를 가를 수 없다.
- 단계 이름("확인", "제출")으로 가르면 안 된다. 사용자 서술을 프로그램이 "이해"하지 않는다(지시문 2절 6, 13절) [읽음].

| 단계 | Q2가 읽는 답 | 사람 판단 | 트리 결과 [S3] | 같은가 |
| --- | --- | --- | --- | --- |
| 6 결과 해석 문장 작성 | `no`, `external`, `no` | ③ 또는 ④ | ③ `Q2` + ④ `GATE` | 같다고 본다 |
| 7 최종 확인·제출 | `no`, `external`, `no` | ④ | ③ `Q2` + ④ `GATE` | 다름 |

지시문 12.1 [읽음]:

> 이것은 통과 기준이 아니라 "공개 예제에서 통과한 도구가 실제 업무에서도 같은 판단을 내는지" 보는 로컬 확인용이다. 다르면 예제를 고치는 게 아니라, 어떤 질문·규칙이 빠졌는지 ADR로 적고 `examples/`에 그 구조를 가진 합성 예제를 추가한다.

지시문 2절 11 [읽음]: "새 규칙·지표를 넣으려면 `examples/*/expected/`에 기대값을 먼저 추가한다."

T-004는 3.3 트리를 그대로 구현한다(classification.md 승인 결정 4). 이 ADR은 그 뒤 방향을 묻는다.

## 후보

### 후보 1. 새 질문 추가 (질문 10개)

- 질문(초안): 키 `human_signoff`, "사람이 책임지고 확인·승인·제출하는 단계인가", 선택지 `yes` / `no`, 기본값 `no`.
- 분기(초안): 트리 맨 앞에 근거 키 `SIGNOFF`. `human_signoff == yes`면 ④. 사람이 책임지는 단계는 기존 기능이 있어도 사람이 한다고 본다. Q1~Q4의 번호와 뜻은 그대로다.
- 근거 문장(초안): `사람이 책임지고 확인·제출하는 단계이므로(yes) 사람이 하는 것으로 분류.`
- 12.1: 7단계에 `yes`를 답하면 ④, 6단계는 `no`로 지금과 같다(**미확인**: 실험 안 함).
- 영향
  - case-schema 4.4 표: 끝에 1행 추가. 파서의 질문 키 목록과 T-003 표 대조 테스트가 같이 바뀐다. 지시문 3.1·3.2의 "질문 9개"도 바뀐다. 지시문은 사람이 고친다.
  - classification.md: 4.1 해석, 4.2 조건 표, 4.5 문장 틀, 4.6 읽은 답 표(모든 근거 키에 새 키), 6.1 예시가 바뀐다.
  - 예제 3종 expected: `answers.yaml`에 새 키가 없으면 기본값이 된다. 그러면 모든 단계 `defaults`에 새 키가 들어간다. 트리가 맨 앞에서 읽으므로 모든 `step` 행 문장에 기본값 표시가 붙는다(4.6 규칙). `answers.yaml`에 `human_signoff: no`를 적으면 expected 바이트는 그대로다(**미확인**). 어느 쪽이든 사람이 확정한 파일(승인 결정 14)이 바뀐다.
  - 행 모델 A: 그대로. `SIGNOFF`는 부가 행이 아니다. `step` 행의 담당을 ④로 만든다. 12절 "최종 확인·발송 = ④"는 지금처럼 게이트 행으로 읽는다(승인 결정 1 유지).
  - 겹침: 앞 단계가 `external`이고 다음 단계가 `human_signoff: yes`면, 같은 사람 확인이 게이트 행과 사용자 단계로 두 번 나온다. 12.1의 6·7단계가 이 모양이다.
  - 게이트: 3.3 원문은 "항상"이다. `SIGNOFF` 단계 뒤에도 게이트 행을 붙일지 정해야 한다.
- 좋은 점: 빠진 것이 질문이라 질문으로 메운다(2절 6). 6단계와 7단계를 가르는 유일한 후보다.
- 나쁜 점: 바뀌는 곳이 가장 많다. 승인된 T-003 스키마와 지시문 3.2를 바꾼다. 인터뷰 질문이 단계마다 하나 늘어난다.

### 후보 2. 규칙 추가 (기존 답만 사용)

- 규칙(초안): Q2를 나눈다. `rule_expressible == no`이고 `failure_impact in {external, safety_legal}`이면 ④. 아니면 지금처럼 ③.
- 12.1: 6·7단계 모두 ④. 7단계는 사람 판단과 같다. 6단계도 "③ 또는 ④"에 든다(**미확인**: 실험 안 함, 표로 추론).
- 영향
  - case-schema 4.4 표: 그대로. 파서도 그대로.
  - 지시문 3.3 Q2의 결과가 바뀐다. classification.md 4.1·4.2·4.5·4.6이 바뀐다. 6.1의 `rule_expressible: no, failure_impact: external` 행(지금 ③ `Q2` + ④ `GATE`)이 바뀐다.
  - 예제 3종 expected: 그대로. 세 예제에 `rule_expressible: no` 단계가 없다 [읽음 classification.md 7.2~7.4].
  - 행 모델 A: 그대로. 이 단계는 ④ `step` + ④ `GATE`로 ④가 두 행이 된다("항상" 그대로일 때).
- 좋은 점: 질문·스키마·예제가 그대로다. 바뀌는 곳이 적다.
- 나쁜 점: "책임"을 묻지 않고 다른 답으로 짐작한다. 6단계와 7단계를 가르지 못한다. "기준을 글로 못 쓰고 틀리면 외부 영향"인 단계(예: 밖으로 나가는 문장 초안)에서 ③ 제안이 사라진다. AI가 도울 곳을 찾는 도구가 그 후보를 가린다.

### 후보 3. 현행 유지 (차이만 기록)

- 트리·질문·예제 모두 그대로. 7단계 ③ + ④ 게이트를 "④ 게이트가 있으니 사람이 책임진다"로 읽는다.
- 12.1 7단계는 "다름"으로 이 ADR에 남는다.
- 영향
  - case-schema 4.4 표, 예제 expected, 행 모델 A: 모두 그대로.
  - 12.1의 "합성 예제 추가"를 지키기 어렵다. 같은 구조의 예제를 넣으면 사람 판단과 다른 ③을 정답으로 굳힌다. 안 넣으면 규정 뒷부분을 건너뛴다.
  - 평가서(지시문 3.5 목차 2·3)에 7단계가 ③으로 나온다. README "사례" 요약의 ② 비율·③ 단계 수가 사람 판단과 다르다.
- 좋은 점: 지금 바꿀 것이 없다.
- 나쁜 점: 알려진 차이를 그대로 둔다.

### 규칙 (결정을 스펙 말로. T-008 스펙의 출발점)

- 트리: `SIGNOFF`(`human_signoff == yes`)가 맨 앞이다. 걸리면 ④ `step` 행 하나로 멈춘다. `PARTIAL`·`GATE` 행을 붙이지 않는다. Q1~Q4·`ELSE`의 번호와 뜻은 그대로다.
- 지시문 3.3 "항상: failure_impact … 게이트 추가"에 `SIGNOFF` 예외가 생긴다. 지시문은 사람 결정 뒤 리드가 고친다.
- 읽은 답(classification.md 4.6): `SIGNOFF`는 `human_signoff` 하나다. 게이트를 안 붙이므로 `failure_impact`를 읽지 않는다(**해석**). 다른 근거 키는 지금 목록에 `human_signoff`가 더해진다.
- 그래서 `human_signoff`가 기본값(키 없음)이면 모든 `step` 행 문장에 "(기본값 사용, 확인 필요)"가 붙는다(4.6 규칙). 결정의 "명시해서 채운다"가 이것을 막는다. exe 마법사와 스킬 모두 모든 단계에 값을 적는다(ADR 0004).
- 문답의 서명 단계 질문에서 아무 단계도 고르지 않으면 모든 단계를 `no`로 적는다. 이 질문에서는 Enter가 "기본값"이 아니라 "없음"이다(**해석**).
- 근거 문장(초안): `사람이 최종 확인·서명하는 단계이므로(yes) 사람이 하는 것으로 분류.` T-008 스펙에서 확정한다.
- AI 과잉 후보(4.8): `SIGNOFF` 단계는 ④라 후보가 아니다. 확인 항목(4.7)은 그대로다.
- 12.1 합성 사본에 7단계 `yes`, 나머지 `no`를 넣으면: 7단계 ④ `SIGNOFF` 한 행, 6단계 ③ `Q2` + ④ `GATE`. 행 수(모델 A) 10 → 9(**미확인**: 실험 안 함, 표로 추론).

### 예제 3종 expected가 바이트 그대로일 것으로 보는 이유 (**미확인**)

- 직접 쓴 `no`는 `IsDefault = false`다(case-schema 4.4). `defaults`에 들어가지 않고 문장 표시도 없다(4.6).
- `SIGNOFF`에 안 걸리면 트리는 지금처럼 Q1부터 간다. 문장에는 그 잎을 정한 답만 쓴다(4.5). "아니다"로 넘어온 답은 쓰지 않는다. 그래서 문장이 같다.
- T-008이 실제로 돌려 확인한다. 하나라도 바뀌면 멈추고 juhan에게 보고한다(결정).
- 순서상 T-007(`schema_version`, ADR 0004)이 먼저다. "그대로"는 T-007이 만든 바이트를 뜻한다.

- 스펙 블록: classification.md 7.2~7.4의 `answers.yaml` 블록, synthetic-examples.md 7.2~7.4의 `case.yaml` 블록과 SHA-256 줄 [읽음]. 합성 CSV는 답 값을 쓰지 않을 것으로 보지만, SHA-256이 그대로인지 T-008이 확인한다(**미확인**).
- case-schema 4.4 표에 1행(표 끝). `StepAnswers`에 10번째 답. 공개 API 변경이다(T-003 승인 결정 14). `CaseApiShapeTests`가 `StepAnswers`를 이름 붙은 인자 9개로 만든다 [읽음]. 이 테스트 코드를 고쳐야 컴파일된다.
- 분류 테스트 입력: 기준 답(classification.md 6.1)에 `human_signoff`가 없으면 기본값이 되어 모든 문장에 표시가 붙는다. 6.2 표의 "문장 표시 없음" 행들이 깨진다. 기준 답에 `human_signoff: no`를 더해야 한다(남은 질문 4). 4.5 문장 대조 조합(2,160개)은 둘로 늘어난다.
- 지시문 3.1 "질문 9개", 3.2 표, 3.3 트리. 사람 결정 뒤 리드가 고친다.
- G2·G3 표본 `TestData/guard/case-valid`은 키가 없어 기본값 표시가 늘어난다. 같은 실행 안에서 비교하므로 통과할 것으로 본다(**미확인**).

## 남은 질문 (juhan 답 대기)

1. **앞 단계 게이트와 `SIGNOFF`가 이어질 때.** 12.1의 6단계(③ `Q2` + ④ `GATE`) 다음 7단계(④ `SIGNOFF`)처럼 사람 확인이 두 번 나온다.
   - 제안: 그대로 둔다. 트리는 단계마다 따로 정하고 앞뒤 단계를 보지 않는다.
2. **4번째 예제의 이름과 순서.** 지시문 2절 11은 "새 규칙·지표를 넣으려면 `examples/*/expected/`에 기대값을 먼저 추가한다"다 [읽음]. 결정 순서는 T-008(규칙) 뒤에 별도 카드(예제)다. CI가 녹색이어야 머지되므로, 실패하는 예제를 먼저 머지할 수는 없다.
   - 제안: 이름 `signoff-final`(가칭). T-008 바로 다음 카드. T-008은 `SIGNOFF` 분기를 단위 테스트로 막는다. 2절 11과의 순서 차이는 이 ADR에 적고, 지시문 12절·M1 G1의 "공개 예제 3종"은 그 카드에서 "4종"으로 고친다. 2절 원칙에 걸리므로 juhan이 답한다(상시 승인 예외, ADR 0004).
3. **`case.yaml`도 같이 고치나.**
   - 제안: 예. `answers.yaml`과 같은 줄에 `human_signoff: no`를 더하고, synthetic-examples.md 7절 블록·SHA-256 줄을 같이 고친다. `examples/` 변경이라 PR 전에 juhan 확인을 받는다.
4. **분류·스키마 테스트 입력에 `human_signoff: no`를 더하는 것.**
   - 제안: 기대값은 그대로 두고 입력만 명시하는 변경으로 본다. `CaseApiShapeTests`의 생성 인자 추가도 같다. 약화가 아니지만 기존 테스트 수정이라 PR 본문에 이유를 쓰고 reviewer가 본다. juhan이 완화로 보면 따로 묻는다.
5. **case-schema 4.4의 단계별 질문 문구와 근거 문장.**
   - 제안: 표 문구 "사람이 최종 확인·서명하는 단계인가". 문장 `사람이 최종 확인·서명하는 단계이므로(yes) 사람이 하는 것으로 분류.` T-008 스펙에서 확정한다.

## 영향

- 이 ADR만으로 바뀌는 파일은 없다. T-004 구현과 예제 3종은 T-008 전까지 그대로다.
- T-008 카드(목표): `human_signoff` 질문과 트리 맨 앞 `SIGNOFF`를 넣는다. `yes` 단계 뒤에는 게이트 행이 없다. 예제 3종 `answers.yaml`(남은 질문 3이면 `case.yaml`도) 모든 단계에 `human_signoff: no`를 적고, `expected/classification.json`은 바이트 그대로(바뀌면 멈추고 보고). 순서는 ADR 0004 "순서"의 4번이다.
- 4번째 예제 카드: T-008 뒤(남은 질문 2).
- ADR 0004: exe 마법사와 스킬은 서명 단계를 한 번만 묻고 모든 단계에 값을 적는다.
